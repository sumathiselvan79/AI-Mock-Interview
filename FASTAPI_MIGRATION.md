# FASTAPI_MIGRATION.md

Tracks the full conversion of the backend (gateway, all 7 agents, all 8 MCP tool
servers, shared packages — STT, TTS, resume parsing, LLM integrations, everything)
from the existing TypeScript/Node implementation to Python/FastAPI. Companion to
`TRACKING.md`, which documents the original 8-stage TS build this is porting.

**Why this doc exists separately from `TRACKING.md`:** this is a long-running,
multi-session conversion driven by an explicit goal. Progress needs to survive
context resets, so state lives here in git, not only in conversation memory.

## Architectural decision

The TS backend's own Stage 1 notes are explicit that despite the CLAUDE.md
diagram, **MCP servers currently run in-process behind the `McpServerHandler`
interface** — not as separate deployable processes. `apps/gateway/src/app.ts`
constructs every agent/tool as an in-process handler and registers it with one
`McpGateway`. The Python port preserves that reality faithfully: **one FastAPI
process** (`backend/app`) owns HTTP + WebSocket routes, the MCP Gateway
(auth/rate-limit/schema-validate/telemetry), and every agent/tool as an
in-process handler module under `backend/app/agents/*` and `backend/app/tools/*`,
each implementing the same `McpServerHandler`-equivalent seam. This keeps every
service trivially extractable into a real separate process later (swap the
transport, not the interface) without inventing 15 separate Python
microservices no one asked for.

Everything else is ported 1:1: same DB schema (SQL migrations copied verbatim —
Postgres doesn't care what language wrote them), same JSON MCP schemas (copied
verbatim, validated with `jsonschema` instead of `ajv`), same REST/WebSocket
wire contracts (so `apps/web` needs no changes beyond its backend base URL),
same state machine, same auth token format, same telemetry event types.

## Directory layout

```
backend/
  pyproject.toml
  app/
    main.py                 # ~ index.ts — uvicorn entrypoint
    config.py                # ~ config.ts
    logging_.py              # ~ logging/logger.ts
    paths.py                 # ~ paths.ts
    gateway.py                # ~ app.ts — create_app() composition root
    auth/                      # ~ auth/*.ts
    http/routes/                # ~ http/routes/*.ts
    http/live_channel.py         # ~ http/live-channel.ts (WebSocket)
    mcp/                           # ~ mcp/*.ts — gateway, schema validation, dev-ping
    storage/                        # ~ storage/*.ts — ports + memory/postgres/redis drivers
    agents/                           # ~ /agents/* — harness, resume_service, question, followup, coding, time_tracking, memory, report
    tools/                             # ~ /mcp-servers/* — resume_parser, eval, time_tracking, telemetry, clipboard_monitor, focus_monitor, speech_service, llm_provider
    shared_types/                       # ~ packages/shared-types — Pydantic models
    interview_domain/                    # ~ packages/interview-domain
    llm_client/                           # ~ packages/llm-client
  mcp_schemas/                # ~ packages/mcp-schemas/schemas — JSON files copied verbatim
  migrations/                  # ~ apps/gateway/migrations — SQL copied verbatim
  tests/
```

## Notes for whoever (human or AI) picks this up mid-stream

- Read the TS source file being ported before writing its Python equivalent —
  most files carry load-bearing comments (`soul.md` references, why a check
  exists) that are easy to silently drop in a rewrite. Preserve the *reasoning*
  comments, not just the code.
- Storage has two drivers behind one port in the TS version
  (`STORAGE_DRIVER=memory` default, `postgres` for real infra) — port both, in
  that order (memory first unblocks everything else without needing Postgres
  installed).
- The MCP schemas in `packages/mcp-schemas/schemas/*.json` are the contract.
  Don't hand-translate them into Pydantic models as the source of truth — load
  and validate against the JSON files directly (via the `jsonschema` package),
  same as the TS side does with `ajv`, so the two can never drift.
- `soul.md` and `INSTRUCTIONS.md` govern behavior/ethics and exact schemas
  respectively for every agent — read the relevant section before porting an
  agent's judgment logic, not just its plumbing.
